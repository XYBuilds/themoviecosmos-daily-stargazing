# 新闻源选择与自动化边界：新闻侧全自动、section 宽进、tone 抽取、热度后置

**Status**: accepted（Phase 5.4 抓取源改进期拍板；热度算法D4与小快灵D6为Post-MVP方向登记）

> **本 ADR 的性质**：记账型。本文承接多轮产品讨论，把「新闻源选择策略 + 自动化边界」钉成正式决策，消除 [PRD §6](../SSOT/电影宇宙「每日星轨观测」系统%20PRD.md) 与 Phase 5/6 计划中关于 `--pick` 的口径冲突。
>
> 详细实现设计见 [`news-source-selection-design.md`](../SSOT/news-source-selection-design.md)。本文只锁定产品/架构口径：新闻侧如何进、哪里不许人工介入、什么机制才是真正选题闸门，以及哪些收敛手段属于 Post-MVP 或开发者体验。

## 背景

「电影星球观测」的主流程是：抓 Guardian 新闻（事件侧）→ extract / expand → 12 persona agents 联想 → embedding 从电影库召回候选电影 → judge 打分 → 人工审核编辑挑选电影 → LLM 写稿发社媒。

这里存在一个容易混淆的边界：系统到底是在**人工挑新闻后找电影**，还是在**自动选择新闻后让人只挑电影**。

PRD §6 的原始口径是「选新闻：按热度 Top1；评测期允许人工指定」。也就是说，人工指定新闻只是评测期手段，不是生产默认入口。但此前 Phase 5 / Phase 6 计划把 `fetch_news --pick`（人工挑新闻）写成默认入口，容易把产品形态改成「人先挑新闻」。这与本项目「自动发现每日热点，再让总编在电影侧做最终判断」的定位冲突。

同时，Phase 5.4 抓取源改进讨论还确认了三件事：

1. Guardian section 不应承担强选题职责；真正的选题闸门应是热度排序。
2. Guardian 文章体裁差异很大，抽取策略不能继续盲取前 5 段。
3. 在热度机制未完成前，系统允许用高成本全量跑通，以换取产品链路尽快闭环。

因此，本 ADR 把这些口径一次性登记，供 Phase 5/6 及后续自动化实现对齐。

## 决策

### D1 · 新闻侧全自动，流程中段禁止人工审核新闻

| 条目 | 定稿 |
| --- | --- |
| **产品硬约束** | 新闻侧必须全自动；流程中段不设置人工审核新闻、人工挑新闻、人工改新闻队列等生产默认环节。 |
| **唯一人工介入点** | 人工只保留在电影侧：总编从「召回并打好分的候选电影」中挑 1 部，或决定不发。 |
| **`fetch_news --pick` 口径** | `--pick` 降级为评测/调试开关，不是生产默认入口；不得把它写成主流程必经步骤。 |
| **与 PRD §6 对账** | PRD §6 写的是「选新闻：按热度 Top1；评测期允许人工指定」。本决策是回归 PRD 原意，而非新增产品发明。 |
| **边界含义** | 系统可以暴露调试入口让开发者指定新闻，但生产语义仍是「自动选新闻 → 人工选电影」。 |

### D2 · section 宽进黑名单制

| 条目 | 定稿 |
| --- | --- |
| **旧口径** | 用白名单精选 section，让少数 section 进入后续链路。 |
| **新口径** | 改为「默认全放行，只排除结构性非内容」。section 不再承担主要选题职责。 |
| **黑名单 1 · 行业垂直 / B2B / professional** | 所有 `*-network`，以及 professional 后缀类 section。 |
| **黑名单 2 · Guardian meta / 工具页** | `about` / `community` / `crosswords` / `extra` / `guardian-foundation` / `help` / `info` / `jobsadvice` / `katine` / `membership` / `search` / `theguardian` / `theobserver` / `thefilter` / `thefilter-us`。 |
| **黑名单 3 · 纯功能页** | `weather` / `travel-offers`。 |
| **黑名单 4 · 地方新闻** | `local` / `cardiff` / `edinburgh` / `leeds` / `cities`。 |
| **黑名单 5 · 低事件旅行内容** | `travel`；它以游记散文 / 攻略服务为主，极少完整公共事件，个性化强、难形成共鸣。 |
| **其余 section** | 全部放行，包括 `film` / `culture` / `education` / `food` / `sport` 等；`culture` 等混合 section 既有公共事件也有个性化随笔，section 级不处理，后者归 D4 热度排序。 |
| **理由** | 匹配失败成本低，宁放勿缺；真正的选题闸门是热度排序（见 D4），不是 section。 |

### D3 · tone 标签驱动的格式感知抽取 + tone DROP 结构闸门

| 条目 | 定稿 |
| --- | --- |
| **实证基础** | Guardian API `show-tags=all` 返回 `tone/*` 标签；已抽样 240 篇，tone 覆盖率 97.1%。 |
| **替代旧行为** | 用 tone 驱动抽取策略，替代「盲取前 5 段」。 |
| **抽取表边界** | `EXTRACTION_TABLE` 只决定「抽几段」，不做整条丢弃；硬新闻 `tone/news` 取前 5 段，`tone/recipes` 只取 lede，`tone/features` 走段长衰减启发式，无 tone 默认前 3 段。 |
| **tone DROP 黑名单** | 新增 `tone/minutebyminute` / `tone/letters` / `tone/competitions` 文章层 DROP；三者分别是即时直播流水、读者来信、投稿/征集，缺少完整起因-经过-结果叙事结构。 |
| **DROP 优先级** | DROP 检查优先于多 tone 仲裁与抽取；只要任一 tone 命中 DROP 黑名单，整条丢弃，即使同时带 `tone/news` 也不能救回。 |
| **多 tone 仲裁** | 非 DROP 文章按「具体度」仲裁，优先采用信息更强、更能决定版式的 tone；具体体裁（如 `recipes`）优先于泛化体裁（如 `news` / `features`）。 |
| **`tone/features` 特例** | `tone/features` 占比最高（107/240），但它是「体裁黑洞」，无法单靠标签判断结构；回退到「段长衰减比」启发式。 |
| **与 section 黑名单边界** | section 黑名单（D2）排除结构性不合适的整个 section；tone DROP 在文章层按体裁结构丢弃少数非事件体裁。 |
| **与 D4 热度边界** | 个性化随笔是否低共鸣属于语义级选题价值判断，归 D4 热度排序；不得用 tone 或相似度提前冒充热度 / 共鸣价值判断。 |
| **明确反对** | 绝不能用「新闻原文表层文本相似度」做任何筛选；这会与项目追求「深层共振、非字面联想」的灵魂冲突。 |

### D4 · 热度排序是核心选题机制（Post-MVP 实现）

| 条目 | 定稿 |
| --- | --- |
| **产品核心** | 本项目不是「随便找新闻配电影」，而是「给最热的几条新闻找共振电影」。 |
| **Guardian API 限制** | 已确认 Guardian Content API 的 `order-by` 只支持 `newest` / `oldest` / `relevance`，不提供热度 / popularity / most-viewed 字段。 |
| **自研方向** | 热度需要自研；PRD §6 已规划基本思路：「多源同事件计数 + 时间近端加权」。 |
| **实现阶段** | 热度排序是 Post-MVP 机制，不在本 Phase 5.4 实现。 |
| **职责 1 · 产品** | 只推最热选题，保持「每日热点观测」的产品承诺。 |
| **职责 2 · 开发** | 取 TopN 即可形成小快灵样本，让开发迭代不必每天吞全量新闻。 |
| **职责 3 · 成本** | 天然收敛喂给 agents 的新闻条数，减少后续 persona / judge 调用。 |

### D5 · 初期全量喂 agents，不设前置共振闸门

| 条目 | 定稿 |
| --- | --- |
| **价值排序** | 用户价值观是「人力最贵」；初期可以牺牲金钱/时间成本，先把完整链路跑通。 |
| **前置闸门口径** | 初期不在 agents 前设置「共振可能性」筛选闸门；新闻进入后直接跑完整链路。 |
| **单条成本测算** | 单条新闻走完整链路约 46 次 LLM 调用。 |
| **主要成本头** | 12 persona × 2 ≈ 24 次；judge 逐候选 ≈ 19 次。两者是主要成本头。 |
| **日级成本估算** | 每日全量 20–25 条约 920–1150 次 LLM 调用/天。 |
| **阶段性接受** | 初期接受此成本，以换取链路闭环与真实分布数据；待热度排序（D4）实现后，再用 TopN 收敛。 |
| **反直觉发现** | judge 逐候选打分（约 19 次，且默认 thinking 模式）是与 persona 几乎同量级的隐藏成本头。未来压成本时，judge 与 persona 同等重要。 |
| **与既有 ADR 对账** | 这延续 [ADR-0010 D4](0010-pseudo-drop-granularity-and-pipeline-first-derisking.md) 对 judge 债的记录，也受 [ADR-0007 D4](0007-logic-resonance-judge-prescreen-and-pov-focalization.md) 的 judge 阈值纪律约束：judge 不能在未校准分布上被当作静默删除器。 |

### D6 · 开发期「小快灵」是独立于产品的开发者工具

| 条目 | 定稿 |
| --- | --- |
| **问题拆解** | 快速迭代慢有两层原因：①新闻条数多；②单条内部约 46 次串行 LLM 调用，即使只跑 1 条仍慢。 |
| **砍新闻条数** | `--limit` 可以减少新闻条数，但只解决第一层慢。 |
| **砍 persona 成本** | 可考虑 `--personas N`，只跑少数 persona，用于开发期快速验证链路。 |
| **砍 judge 成本** | 可考虑 `--judge-topk`，限制进入 judge 的候选数。 |
| **并行化方向** | persona 并行化可缩短 wall-clock time，但不改变产品语义。 |
| **缓存方向** | 可用上游产物缓存，例如 `--deconstruction-file` 复用 extract / expand 结果，避免重复跑前段。 |
| **产品边界** | 这些都是开发者体验工具，不是产品选题机制；不得把开发期捷径解释为生产默认语义。 |
| **本文范围** | 本 ADR 只登记方向，不规定具体 CLI 形态、默认值或实现顺序。 |

## 为什么

这批决策是一组连贯口径，而不是六个孤立优化：

1. **D1 先锁自动化边界**：新闻侧全自动，人工只在电影侧做总编判断，避免产品退化成「人先挑新闻」。
2. **D2 把 section 从选题职责中解放出来**：section 只做结构性排除，宁放勿缺；真正的选题责任交给 D4 热度排序。
3. **D3 保证喂给 agents 的信噪比**：既然 D2 会宽进，就必须用 tone 感知不同体裁；抽取表只负责抽几段，tone DROP 只负责丢弃直播、来信、投稿征集这类无完整事件叙事结构的文章。
4. **D5 让 MVP 先跑通**：在 D4 未实现前，不再叠加前置共振闸门；用全量 + 高成本换完整链路闭环。
5. **D4 / D6 是后续收敛手段**：热度排序从产品、开发、成本三方面收敛新闻规模；小快灵开关只服务开发体验，不改变生产产品语义。

因此，Phase 5.4 的重点不是做一个更精致的 section 白名单，也不是恢复人工挑新闻，而是把「宽进 → 格式感知抽取 → 全自动跑通 → Post-MVP 热度收敛」这条主线固定下来。

## 后果 / 已知局限

- **D4 未实现前，新闻侧没有真正选题闸门**：这是已知临时状态。初期依靠全量进入 agents + 高成本跑通，而不是依靠热度 TopN 收敛。
- **成本会在短期显著上升**：每日 20–25 条全量新闻意味着约 920–1150 次 LLM 调用/天。该成本是为了换真实分布与端到端闭环，不代表长期生产形态。
- **judge 分布校准挂起**：原 plan 5.4 中的 judge 分布校准因新闻分布尚未稳定而挂起；在热度机制与真实输入分布明确前，不应冻结 judge 阈值或把 judge 当生产删除器。这与 [ADR-0007 D4](0007-logic-resonance-judge-prescreen-and-pov-focalization.md) 的阈值纪律一致。
- **`--pick` 仍可存在，但语义变窄**：它只能服务评测、调试、复现，不得成为生产默认入口。
- **section 黑名单会漏掉少量低价值内容**：这是 D2 选择「宁放勿缺」的必然后果；后续由 D4 热度与 D3 抽取质量控制，而不是用 section 白名单提前砍掉潜在选题。
- **section / tone DROP 仍只处理结构边界**：`travel` 与三类 DROP tone 是因事件叙事结构不适合而排除；个性化随笔的低共鸣问题仍归 D4 热度排序，不能用 tone 或相似度做语义价值捷径。
- **小快灵方向未定实现**：D6 只登记开发者体验方向，不承诺具体开关名、默认值、并行模型或缓存协议。
